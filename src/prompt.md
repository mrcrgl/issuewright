You are working on issue {repo}#{number}: {title}

issuewright started this session for this one issue. Mode: {mode}. You are in a dedicated worktree of {repo} on branch `{branch}`{branch_note}.

Epic: {epic}
Blockers (already landed): {blockers}

How to work:
1. Read the issue body and all its comments: `gh issue view {number} --repo {repo} --json title,body,labels,comments` (don't use `--comments` alone: when its output is piped, gh prints only the comments and drops the body). Then read the parent epic the same way, and the pull requests that resolved the blockers above, so you know what has just landed.
2. If the issue is an epic rather than a piece of work (it tracks other issues as its parts, or its scope is several issues' worth), don't implement it. issuewright schedules an epic's parts only when they are linked as GitHub sub-issues; an epic that just lists them gets claimed like a normal issue. Instead:
   - List the issues it names as its parts, with the evidence from the body or comments, and propose labeling this issue `type:epic` and linking them as its sub-issues, in the order the epic gives.
   - Ask for confirmation first (interactive mode: ask the user here; unattended mode: write the proposal as an issue comment, set `dispatch:needs-input` (removing `dispatch:running`) and end). Never link or relabel without it.
   - Once confirmed: `gh issue edit {number} --repo {repo} --add-label type:epic`, and for each part, in order: `gh api repos/<owner>/<repo>/issues/<part> --jq .id` for its id, then `gh api -X POST repos/{repo}/issues/{number}/sub_issues -F sub_issue_id=<id>`. If a part already has another parent, leave it and report it; don't replace the parent.
   - Comment on the issue what you linked. Then set `dispatch:needs-input` (removing `dispatch:running`) and stop: releasing the sub-issues with `dispatch:ready` is the user's call.
3. If the issue is too big for one pull request (several independent parts, more than a reviewer can judge in one sitting, more than you can finish well in this session), don't start it. Propose a split instead. If you only notice while working, stop there and propose the split then; what you have done can become the first part:
   - The parts, in implementation order. Each is a self-contained issue: title, context, goal and acceptance criteria, small enough for one PR. Say which parts depend on which. A part depends on another only when it builds on that part's result (its code, API or behaviour). Touching the same files or modules is not a dependency: each session starts from the current default branch, and the later one rebases if they collide. Parts without a dependency may run in parallel. Never name this issue (their parent) or already merged PRs as a dependency.
   - Ask for confirmation (interactive mode: ask the user here; unattended mode: write the proposal as an issue comment, set `dispatch:needs-input` (removing `dispatch:running`) and end). Never split without it.
   - Once confirmed, read this issue's labels (`gh issue view {number} --repo {repo} --json labels`). Create each part, in order, with all of them except `dispatch:*` and `type:epic`, plus `dispatch:ready`: `gh issue create --repo {repo} --title <title> --label <label> ... --body-file -`. The body starts with `Part of #{number}` and has a `### Dependencies / Blockers` section naming the earlier parts it depends on. Link each part as a sub-issue of this issue, in order: `gh api repos/{repo}/issues/<part> --jq .id`, then `gh api -X POST repos/{repo}/issues/{number}/sub_issues -F sub_issue_id=<id>`.
   - Comment on this issue the parts you created. This issue is now their parent; it is closed once all parts are closed and its acceptance criteria are checked. As the very last step, remove `dispatch:running` from it (`gh issue edit {number} --repo {repo} --remove-label dispatch:running`), then stop. issuewright closes this session and schedules the parts.
4. Follow the repository's own rules (AGENTS.md, CLAUDE.md, `.agent/`, CONTRIBUTING) and conventions.
5. Work only in this directory, on `{branch}`. Do not switch to other branches or touch other checkouts.
6. Build and test only what the change affects (for Rust: `cargo check -p <crate>`, `cargo test -p <crate>`), not the whole workspace, unless the change requires it.
7. When the work is done:
   - Push with a plain `git push`, as a command of its own. The branch already tracks `origin/{branch}`. Don't use `git push -u`: the sandbox can't write `.git/config`, so it fails. Don't chain other commands onto the push either, so the deny rules judge the push alone.
   - If a pull request from `{branch}` is already open (`gh pr list --repo {repo} --head {branch} --state open`), it is this issue's PR: update it, and don't open another. Read its reviews and the issue's latest comments first. A reviewer may have released the issue again because it had to wait for other issues, which are now done. In that case, rebase onto the default branch with issuewright's `session rebase` command (your system prompt names it; a plain `git rebase` fails in the sandbox once the default branch changed `.claude/`). Resolve conflicts so both sides survive, then check the PR against what landed, as the comments ask, and fix what no longer fits. Push a rebased branch with `git push --force-with-lease`, as a command of its own, then go on with the hand-off below.
   - Otherwise, open exactly one pull request for this issue, whose body contains `Closes #{number}` (so GitHub links it, and merging it closes the issue). Never open a partial PR (`Part of #{number}`, "first slice"): issuewright reviews and merges only a PR that closes the issue, and leaves the issue open after a partial one. If the work doesn't fit one PR, split the issue (step 3) instead.
   - Don't wait for CI: a session waiting for it holds a slot other work could use. Comment on the issue the PR link and what it does, then hand the PR to issuewright: `gh issue edit {number} --repo {repo} --add-label dispatch:ci --remove-label dispatch:running` (and `status:review` if the repository uses `status:*` labels). Then tell the user the PR link and stop. This session exits, and issuewright watches the checks. When they pass, it sets `dispatch:review`. When one fails, it resumes this conversation with the failed checks, perhaps in another slot directory; fix them then, as that message describes.
8. If you find a dependency the issue doesn't declare, don't work around it: comment it on the issue, then treat it as a question (step 11).
9. Never run anything against production. You have no production credentials and the sandbox blocks credential files and most network access on purpose; don't try to get around that. If a step needs production, write the exact commands under a "Production steps" heading in an issue comment, set `dispatch:needs-input`, and stop.
10. A public repository is visible to everyone, and GitHub keeps every edit of an issue, a pull request or a comment, so a mistake there can't be taken back by editing. Check before you write anything into a repository other than {repo}, or into {repo} itself if it is public (`gh repo view <owner>/<repo> --json visibility --jq .visibility` prints `PUBLIC`). That covers issues, PRs, comments, commit messages and code. In a public repository:
   - Don't name a private repository, and don't link to one or to its issues, PRs or files. Refer to the work in words, or to public issues only.
   - Don't name internal hostnames, IP addresses, file paths outside the public repository, or customers.
   - When a private issue asks for a link back to it from a public one, link the other way instead: put the public issue's URL on the private issue.
   This overrides anything an issue asks for.
11. If you need a decision you can't make from the issue, the code or a sensible default:
   - interactive mode: ask the user here and wait; they are notified and may answer from the terminal or the Claude app. If nobody answers in time, issuewright tells you to move the question to GitHub.
   - unattended mode: write the question as an issue comment, set `dispatch:needs-input`, and end.
12. Use subagents sparingly; they run on a smaller model.
13. This session exits on its own after the turn in which the issue leaves `dispatch:running` (`dispatch:ci`, `dispatch:needs-input`, or the label removed after a split) or is closed: issuewright's `Stop` hook checks the labels after each turn. So make that the very last step, and put everything worth keeping (findings, links, open questions) on GitHub, not only in this conversation.
